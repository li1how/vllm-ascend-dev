# vllm-ascend-dev 工作区构建 Skill

针对 vllm-ascend-dev 开发工作区的结构变更、文件新增/删除、配置调整等操作，提供安全可控的工作流：扫描 → 分析 → 方案 → 确认 → 执行 → 联动 → 审视 → 手动 Git。

---

## 触发词

构建工作区、调整工作区、更新工作区、修改工作区、配置工作区、管理工作区、维护工作区、重建工作区、刷新工作区、设置工作区、变更工作区、工作区、workspace、搭建环境、初始化工作区、重新组织、整理工作区、改造工作区

---

## 核心原则

1. **先看后动**: 任何修改前必须先扫描分析当前工作区状态
2. **方案先行**: 给出 2-3 个可行方案，标注优劣，等用户选择后才执行
3. **联动更新**: 修改后同步检查并更新所有受影响的文件
4. **终审把关**: 所有修改完成后，整体审视一遍正确性和合理性
5. **Git 不动手**: 只输出 Git 命令，由用户手动执行

---

## 联动关系发现（运行时构建）

在执行扫描时，根据实际工作区内容构建联动关系：

### 联动发现规则

以下规则用于在执行时自动发现文件间的联动关系，而非硬编码具体文件名：

| 规则 | 发现方式 | 联动逻辑 |
|------|---------|---------|
| **入口文档** | 扫描根目录的 `README*`、`CONTRIBUTING*`、`INDEX*` 等 | 这些文件通常引用和描述其他文件，目录结构/脚本/配置变更时需同步更新 |
| **初始化脚本** | 扫描 `scripts/`、`bootstrap*`、`setup*`、`Makefile` 等 | 脚本中引用的文件路径、克隆的仓库、创建的目录，变更时需同步 |
| **忽略规则** | 扫描 `.gitignore`、`.dockerignore`、`.npmignore` 等 | 新增/删除文件或目录时，检查忽略规则是否需要更新 |
| **工作区/项目配置** | 扫描 `.code-workspace`、`package.json`、`Cargo.toml`、`pyproject.toml` 等 | 目录结构调整时，检查 `folders`、`workspaces`、`packages` 等字段 |
| **Skill/插件注册** | 扫描 `.claude/skills/`、`.claude/settings.json`、插件配置目录 | 新增/删除 Skill 或自动化配置时，检查是否需要更新项目级配置 |
| **IDE 配置** | 扫描 `.vscode/`、`.idea/`、`.editorconfig` 等 | 路径、解释器、格式化配置变更时检查 |

### 构建联动矩阵

第〇阶段扫描完成后，根据实际发现：
1. 列出所有"入口/引用型"文件（README、脚本、配置等）
2. 对每个入口文件，解析其内容，提取它引用了哪些文件或目录
3. 反向建立映射：给定一个被引用的文件，找到所有引用它的入口文件
4. 将此矩阵作为后续联动检查的依据

示例输出格式（由扫描结果动态生成）：

```markdown
### 联动关系矩阵（基于扫描结果）

| 被引用项 | 引用它的文件 |
|----------|------------|
| {被引用项路径1} | {入口文件A} (line X), {入口文件B} (line Y) |
| {被引用项路径2} | {入口文件C} (line Z), {忽略规则文件} (line W) |
| {外置依赖目录}/ | {入口文档}, {初始化脚本}, {忽略规则文件}, {工作区配置} |
```

## 执行流程

### 第〇阶段：工作区扫描与分析（必做，不可跳过）

在任何操作前，必须先完整扫描工作区并输出分析报告。

#### Step 0.1: 文件系统扫描

```bash
# 列出所有非忽略文件（排除 .git 目录）
find . -maxdepth 4 -not -path './.git/*' | sort
```

然后读取 `.gitignore`，标注哪些文件/目录被忽略，对比实际存在和版本控制的范围。

#### Step 0.2: 自动发现并读取关键文件

不预设具体文件名，而是按以下策略自动发现入口文件：

1. **入口文档**: 扫描根目录的 `README*`、`INDEX*`、`CONTRIBUTING*`、`GUIDE*` 等，读取了解项目结构描述
2. **忽略规则**: 扫描 `.gitignore`、`.dockerignore` 等
3. **项目/工作区配置**: 扫描 `*.code-workspace`、`.editorconfig`、`package.json`、`Cargo.toml`、`pyproject.toml`、`Makefile`、`CMakeLists.txt` 等
4. **初始化/引导脚本**: 扫描 `scripts/` 目录、`bootstrap*`、`setup*`、`install*`、`init*` 等可执行脚本
5. **IDE 配置**: 扫描 `.vscode/`、`.idea/` 中的配置文件
6. **AI 工具配置**: 扫描 `.claude/`、`.github/copilot*`、`.gemini/` 等

#### Step 0.3: 输出工作区现状报告

以结构化 Markdown 输出当前工作区状态：

```markdown
## 🔍 工作区现状分析

### 基本信息
- 工作区根路径: {实际路径}
- 外置/依赖仓库状态: {仓库名}/ (✓ 已克隆) | {仓库名}/ (✗ 缺失)
- 发现的关键目录: [{dir1}, {dir2}, ...]
- 发现的入口文件: [{file1}, {file2}, ...]
- 发现的脚本: [{script1}, {script2}, ...]
- AI 工具/Skill 清单: [{skill1}, {skill2}, ...]

### 目录结构（实际）
{tree 或 ls -R 精简输出}

### 关键文件一致性检查
{根据实际发现的入口文件和引用关系生成检查项}
| 检查项 | 状态 | 说明 |
|--------|------|------|
| {入口文档} 目录结构与实际一致 | ✓ / ⚠ / ✗ | ... |
| {忽略规则文件} 覆盖所有应忽略项 | ✓ / ⚠ / ✗ | ... |
| {初始化脚本} 引用路径有效 | ✓ / ⚠ / ✗ | ... |
| {工作区配置} folders 与实际目录匹配 | ✓ / ⚠ / ✗ | ... |
| {配置目录} 与内容一致 | ✓ / ⚠ / ✗ | ... |

### 发现的联动关系
{输出运行时构建的联动矩阵}

### 发现的问题
1. {问题描述} — 影响范围: {xxx}
2. ...
```

### 第一阶段：需求确认

根据用户意图和第〇阶段的分析报告，确认具体需求：

1. 用户想要做什么？（新增目录/文件、删除、重组、修复不一致等）
2. 操作的范围和边界是什么？
3. 有哪些约束条件？

如果用户意图模糊，从分析报告中提炼 2-3 个可能的方向让用户选择。

---

### 第二阶段：方案生成与选择（每次操作必做）

对于用户确认的每一项操作，生成 2-3 个可行方案。

#### 方案模板

```markdown
## 📋 方案对比：[操作描述]

### 方案 A：[方案名称] (推荐)
- **做法**: {具体步骤}
- **优点**: {xxx}
- **缺点**: {xxx}
- **影响范围**: {涉及的文件/目录}

### 方案 B：[方案名称]
- **做法**: {具体步骤}
- **优点**: {xxx}
- **缺点**: {xxx}
- **影响范围**: {涉及的文件/目录}

### 方案 C：[方案名称]（可选）
- **做法**: {具体步骤}
- **优点**: {xxx}
- **缺点**: {xxx}
- **影响范围**: {涉及的文件/目录}

---

**请选择一个方案（A/B/C），或提出修改意见。**
```

#### 方案设计原则

- 方案 A 应是推荐方案（最安全、最合理、最符合项目惯例）
- 方案间应有本质区别（不同组织结构、不同抽象层次、不同工具选型），不要只是变量名不同
- 必须标注每个方案的优缺点和影响范围
- 如果只有一个合理方案，说明为什么只有这一种选择，但仍需列出并让用户确认

---

### 第三阶段：执行与联动更新

用户选择方案后执行，并同步检查联动更新。

#### Step 3.1: 执行修改

根据用户选择的方案执行文件操作（创建、编辑、删除、移动）。

#### Step 3.2: 联动检查（每次修改后必做）

根据第〇阶段构建的"联动关系矩阵"，检查所有受影响文件是否需要更新。

方法：从矩阵中查找被本次修改影响的条目，逐项核对引用它的入口文件是否仍然一致。

联动检查通用思路：
```
□ 入口文档类    — 目录结构描述、快速开始步骤、功能说明是否仍然准确
□ 初始化脚本    — 引用的文件路径是否有效、是否有新增步骤需要加入
□ 忽略规则      — 新增物是否被恰当忽略、已删除物的规则是否冗余
□ 项目/工作区配置 — 路径引用、workspace folders、构建目标是否需要更新
□ AI 工具配置   — Skill 注册、自动化配置是否需要调整
□ IDE 配置      — 解释器路径、格式化范围是否需要调整
```

#### Step 3.3: 联动文件修改确认

如果联动检查发现需要修改其他文件，以表格形式列出并让用户确认：

```markdown
## 🔗 联动更新清单

以下文件因本次修改需要同步更新：

| 文件 | 修改内容 | 必要性 |
|------|---------|--------|
| {联动文件1} | {根据联动矩阵确定的具体修改内容} | 必须 / 建议 |
| {联动文件2} | {根据联动矩阵确定的具体修改内容} | 必须 / 建议 |

**是否执行以上联动更新？**
```

## 注意事项

1. **不可跳过扫描**: 第〇阶段扫描分析是强制步骤，即使用户说"不用看了直接做"，也要坚持扫描——没有准确现状就没有正确方案
2. **单次一问**: 如果用户同时提了多个操作需求，逐个处理：完成"方案→确认→执行→联动"循环后再处理下一个
3. **联动不遗漏**: 修改文件后必须检查联动关系矩阵中的所有相关文件，即使只是细微改动也可能需要更新入口文档
4. **审视是质量闸**: 第四阶段审视不是走过场，必须逐项检查并输出完整报告。发现问题就回头修，不要带病交付
5. **Git 只说不做**: 无论用户怎么要求，Skill 范围内不执行 `git add/commit/push/rebase` 等写操作。`git status` / `git diff` 等只读命令可以执行
6. **方案拒绝兜底**: 如果用户拒绝了所有方案，根据反馈重新设计方案再提交
7. **保持项目惯例**: 新增内容遵循项目现有风格（根据第〇阶段扫描识别的代码风格、文档语言、命名约定、注释格式等）。**编写或修改 Shell 脚本时，必须遵循附录 A《Shell 脚本编写规范》**——先阅读 `scripts/` 下的已有脚本作为参考，再动笔。

## 附录 A：Shell 脚本编写规范

以下规范提炼自本工作区已有的三个脚本。**新增/修改 Shell 脚本时必须遵守，执行第四阶段审视时逐项核对。**

### A.1 文件模板

```bash
#!/bin/bash
# ============================================================
# 脚本一句话标题
#
# 详细描述（可选，说明脚本做什么、适用场景）。
# 如有前置依赖，在此注明。
#
# 用法:
#   ./scripts/xxx.sh                         # 默认行为
#   ./scripts/xxx.sh -x | --long-name <val>   # 带参数说明
#   ./scripts/xxx.sh -h | --help              # 查看帮助
# ============================================================

set -e
SCRIPT_DIR="$(cd "$(dirname "$0")/.." && pwd)"
cd "$SCRIPT_DIR"

# ---- 默认配置 ----
...

# ---- 参数解析 ----
print_help() { ... }

while [[ $# -gt 0 ]]; do
    case "$1" in
        -x|--long-name) VAR="$2"; shift 2 ;;
        -h|--help) print_help ;;
        *) echo "[ERROR] 未知参数: $1，使用 -h 查看帮助"; exit 1 ;;
    esac
done

# ---- 环境检查 ----
...

# ---- 主逻辑 ----
...
```

### A.2 参数解析

| 规则 | 示例 | 说明 |
|------|------|------|
| **每个选项一长一短** | `-b\|--with-benchmark`、`-t\|--translate` | 短选项一个字母，长选项描述性命名 |
| **`-h\|--help` 必须** | `-h\|--help) print_help ;;` | 所有脚本统一 |
| **带值选项用 `shift 2`** | `-m\|--model) MODEL="$2"; shift 2 ;;` | 消耗参数名和值 |
| **布尔标志用 `shift`** | `-t\|--translate) DO_TRANSLATE=true; shift ;;` | 只消耗标志本身 |
| **未知参数报错** | `echo "[ERROR] 未知参数: $1，使用 -h 查看帮助"` | 统一 `[ERROR]` 前缀 |

### A.3 帮助信息

```bash
print_help() {
    echo "用法: $0 [选项]"
    echo ""
    echo "选项:"
    echo "  -x, --long-name <val>  参数说明（含默认值）"
    echo "  -h, --help             显示此帮助信息"
    echo ""
    echo "示例:"
    echo "  $0                        # 默认用法"
    echo "  $0 -x val                 # 带参数用法"
    exit 0
}
```

- 帮助标题统一用中文 `用法:`
- 选项行格式: `  -x, --long-name <val>  说明（默认: xxx）`
- 如有多种组合方式，加 `示例:` 段落

### A.4 用法注释（文件头）

紧凑格式，长短选项合并到一行：

```bash
# 用法:
#   ./scripts/xxx.sh                         # 默认行为
#   ./scripts/xxx.sh -x | --long-name <val>   # 带参数
#   ./scripts/xxx.sh -h | --help              # 查看帮助
```

### A.5 错误/日志信息

| 级别 | 格式 | 用途 |
|------|------|------|
| `[ERROR]` | `echo "[ERROR] 描述"` | 致命错误，随后 `exit 1` |
| `[WARN]` | `echo "[WARN] 描述"` | 警告，不中断执行 |
| `[INFO]` | `echo "[INFO] 描述"` | 一般信息 |
| `[OK]` | `echo "[OK] 描述"` | 操作成功 |
| `[SKIP]` | `echo "  [SKIP] 描述"` | 跳过（缩进两个空格，用于子步骤） |
| `[CLONE]` | `echo "  [CLONE] url"` | 克隆操作（缩进两个空格） |
| `>>>` | `echo ">>> 阶段名..."` | 阶段性进度提示 |

### A.6 Bash 风格

| 规则 | ✅ 正确 | ❌ 错误 |
|------|--------|--------|
| 条件测试 | `[[ ]]` | `[ ]`（除非 POSIX 兼容必要） |
| 命令替换 | `$(cmd)` | `` `cmd` `` |
| 变量默认值 | `${VAR:-default}` | 手动 `if [ -z ]` |
| 路径拼接 | `"$DIR/$FILE"` | `$DIR/$FILE`（无引号） |
| 重定向 | `&>/dev/null` | `>/dev/null 2>&1` |
| 数学运算 | `$((a + b))` | `$(expr $a + $b)` |
| 错误时退出 | `set -e`（顶部） | 每个命令手动 `|| exit 1` |
| 局部变量 | `local x`（函数内） | 全局变量污染 |

### A.7 前置操作顺序（固定）

```bash
set -e                                    # 1. 错误即退出
SCRIPT_DIR="$(cd "$(dirname "$0")/.." && pwd)"  # 2. 定位项目根
cd "$SCRIPT_DIR"                          # 3. 切换到项目根
# ---- 加载 .env（如需）----              # 4. 可选：加载环境变量
# ---- 参数解析 ----                      # 5. 解析命令行参数
# ---- 环境检查 ----                      # 6. 检查依赖/环境
# ---- 主逻辑 ----                        # 7. 执行实际工作
```

### A.8 审视清单（第四阶段必检）

- [ ] `set -e` 在脚本顶部
- [ ] `SCRIPT_DIR` + `cd "$SCRIPT_DIR"` 正确
- [ ] 所有选项均有 `-x|--long-name` 双形式
- [ ] `-h|--help` 存在且调用 `print_help`
- [ ] 帮助标题用 `用法:`（中文）
- [ ] 错误信息 `[ERROR]` 前缀统一
- [ ] 用法注释紧凑单行（`-x | --long` 合并）
