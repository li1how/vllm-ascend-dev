# vLLM-Ascend 学习周报 Skill

## 目标

根据用户提供的简要输入，生成一份结构完整、格式规范的 vLLM-Ascend 学习周报。输出为邮件友好的 Markdown 格式，可直接粘贴到邮件客户端发送，也支持在 VSCode 中预览。

## 执行流程

### 步骤 0：搜索并参考已有周报（必做）

在生成新周报之前，**必须先搜索并阅读已有周报**，作为风格、术语、进度追踪的参考依据。

#### 0.1 搜索已有周报

```bash
ls -lt weekly-report/*.md 2>/dev/null
```

#### 0.2 阅读参考策略

| 优先级 | 阅读对象 | 目的 |
|--------|---------|------|
| **必读** | 最近 1-2 期周报（上一期 + 上上期） | 对齐风格、术语、进度百分比；确认"下周计划"是否延续到本周 |
| **建议读** | 更早的周报（如上上月同期） | 了解长期追踪的需求/问题的演进脉络 |

#### 0.3 从已有周报中提取参考信息

阅读时重点关注以下方面，并在生成新周报时加以利用：

| 关注点 | 说明 | 在新周报中的应用 |
|--------|------|-----------------|
| **风格一致性** | 章节结构、标题命名、条目格式、术语用词（如"日志整改" vs "日志优化"） | 保持统一，避免同一事物换不同叫法 |
| **进度追踪** | 上期"下周计划"中的事项是否完成、上期标注"进行中"的进度百分比是否更新 | 在本周内容中体现延续性工作，更新进度百分比 |
| **问题闭环** | 上期表格中"进行中"/"暂缓"的问题是否已解决 | 延续未解决问题到本周，根因/方案有进展则更新 |
| **需求/任务代号** | 如 "B60 三个需求"、"EPLB 特性" 等代号和简称 | 保持一致的任务命名，方便跨周追踪 |
| **技术深度** | 源码学习类条目的展开程度、是否引用代码路径 | 保持相近的详细程度，新模块学习参照旧模块的展开方式 |

#### 0.4 在周报中体现连续性

- 如果本周工作与上期"下周计划"有衔接，在概述中可提及"承接上周 X 工作"、"上周计划的 Y 已完成"
- 如果某项工作是跨周持续推进的（如日志整改），标注整体进度（如"从 10% → 40%"）
- 如果上期遗留问题本周有进展，"根因"和"解决方案"列更新，同时保留追溯线索

### 步骤 1：收集信息

向用户询问以下信息（用户可以用自然语言随意描述，不需要逐项填写）：

1. **报告周期**: 本周起止日期（如用户未提供，默认使用本周一至周五）
2. **本周工作/学习内容**: 学了什么、做了什么（需求进展、源码阅读、功能验证、培训学习等）
3. **遇到的问题**: 遇到了什么困难、如何解决的（如有）
4. **下周计划**: 下一步打算学习/完成的内容
5. **补充信息**: 任何其他需要体现在周报中的内容（如会议、讨论、心得、认证等）

**信息收集原则**:
- 用户可以用任意形式输入，项目符号列表、自然语言段落均可
- 如果用户输入过于简略，主动追问关键细节以便生成充实的周报
- 如果用户明确表示某项没有内容，则对应章节标注"无"或省略
- 对于技术细节（如源码分析、性能数据等），引导用户提供足够的信息使周报内容充实
- **结合步骤 0 的已有周报**，如发现上期"下周计划"中的事项用户未提及，主动询问进展

### 步骤 2：归类与提炼

根据用户输入，将内容归类到以下类别：

| 类别 | 说明 | 典型关键词 |
|------|------|-----------|
| 需求进展 | 需求/任务的推进情况 | 需求、任务、进度、交付、串讲 |
| 源码学习 | 阅读 vllm/vllm-ascend 源码 | 源码、代码、架构、实现、流程、学习了 |
| 功能验证 | 跑通某个功能/模型/场景 | 验证、测试、跑通、部署、serve、拉起 |
| 问题排查 | 定位和修复 bug | 报错、bug、修复、排查、debug、定位 |
| 性能调优 | 性能分析和优化 | 性能、吞吐、延迟、显存、优化、降频 |
| 分享学习 | 参加培训、分享、学课程 | 培训、分享、赋能、CI/CD、课程、认证 |
| 文档撰写 | 编写或翻译文档 | 文档、教程、README、翻译 |
| 交流讨论 | 会议、评审、技术讨论 | 会议、讨论、评审、交流 |

> 类别和条目数量根据实际情况灵活调整。一个条目可能跨多个类别，按主要性质归类。用户的实际工作类别优先于上述分类。

### 步骤 3：生成周报

按照以下模板生成邮件格式的周报。

## 输出格式说明

- **标题**: 使用 `#` H1 标题，格式 `vLLM-Ascend 学习周报（起始日期 - 结束日期）`
- **分隔线**: 使用 `---` 分隔各章节，在大多数邮件客户端中渲染为分隔线
- **问题表格**: 使用 Markdown 表格，状态用文字（已解决 / 进行中 / 暂缓）
- **下周计划**: 使用编号列表而非表格，便于邮件中阅读
- **输出**: 邮件友好的纯 Markdown，不包含邮件头（发件人/收件人/日期），可直接粘贴到邮件客户端发送

## 输出文件名

保存到工作区 `weekly-report/` 目录，使用英文命名：

```
weekly-report/vllm-ascend-weekly-report-YYYY.MM.DD-YYYY.MM.DD.md
```

## 质量要求

1. **内容充实**: 每条工作内容至少包含"做了什么 + 关键细节/收获"，避免流水账
2. **重点突出**: 概述部分让读者 10 秒内了解本周核心产出
3. **技术深度**: 源码学习类条目需展开关键技术要点。如已输出独立分析文档，可简要概括 + "详细学习文档见附件"
4. **计划可衡量**: 下周计划每项要有明确的产出或目标
5. **问题有闭环**: 每个问题记录根因和解决方案，未解决的标注状态
6. **语言专业**: 使用技术术语准确，中文表述简洁通顺
7. **跨周一致**: 任务命名、术语用词、进度百分比与已有周报保持一致；上期遗留问题需在本期体现最新状态

## 示例

### 输入

```
这周是 5.19-5.23。
主要看了 vllm-ascend 的 PD 分离相关代码，理解了 decode 节点和 prefill 节点的交互流程。
还跑通了 DeepSeek-V3 模型在 A3 硬件上的部署，吞吐大概 1200 tokens/s。
遇到一个问题：decode 节点在等待 prefill 节点时超时，后来发现是 KV cache 传输的 shape 不对齐，改了配置之后解决了。
下周打算看 graph mode 的实现，然后尝试适配一个新的 MoE 模型。
另外 CANN 下周要升级到 8.2.RC1，需要关注兼容性。
```

### 输出

```
# vLLM-Ascend 学习周报（2026.05.19 - 2026.05.23）

---

## 一、本周工作概述

本周重点完成了两件事：一是深入学习了 vLLM-Ascend PD 分离架构的代码实现，理解了 prefill/decode 节点的协作机制；二是在 A3 硬件上成功部署了 DeepSeek-V3 模型，推理吞吐达到 ~1200 tokens/s。此外还定位并修复了一个 decode 节点超时的问题。

---

## 二、具体工作/学习内容

### 2.1 源码学习

- **PD 分离架构:** 阅读了 vLLM-Ascend 中 PD 分离的核心实现代码，理清了 prefill 节点和 decode 节点的生命周期、消息传递协议及 KV cache 传输机制。
  - 关键收获：decode 节点通过 RDMA 从 prefill 节点拉取 KV cache，传输的 shape 由 prefill 节点的 `max_model_len` 和 `num_heads` 决定，配置不一致会导致 shape 不对齐
  - 相关代码：`vllm-ascend/vllm_ascend/attention/`、`vllm/distributed/kv_transfer/`

### 2.2 功能验证

- **DeepSeek-V3 部署验证:** 在 A3 硬件上完成 DeepSeek-V3 模型的服务化部署和功能验证。
  - 环境：Ascend A3 (910B), CANN 8.1.RC2
  - 结果：部署成功，推理吞吐 ~1200 tokens/s，功能正常

---

## 三、遇到的问题与解决方案

| 问题 | 根因 | 解决方案 | 状态 |
|------|------|---------|------|
| Decode 节点等待 prefill 节点时超时 | KV cache 传输时 prefill/decode 节点 shape 不一致，导致 decode 端解析失败 | 检查并统一了两端的 `max_model_len` 和 `num_heads` 配置参数 | 已解决 |

---

## 四、下周计划

1. 学习 vLLM graph mode 在 Ascend 上的实现 — 输出 graph mode 源码分析笔记
2. 尝试适配一个新的 MoE 模型 — 完成模型部署并跑通基本推理
3. 关注 CANN 8.2.RC1 升级 — 确认升级后现有功能的兼容性
```

## 注意事项

- 用户输入越详细，生成的周报越充实。如果用户只给了关键词，请主动追问。
- 如果用户说"和上周差不多"，请提醒用户差异化内容更有价值，并引导提供本周的新进展。
- 日期默认使用当前日期，格式为 `YYYY.MM.DD`。用户可以通过输入指定日期范围。
- 输出为邮件友好的 Markdown 格式，可直接全选复制粘贴到邮件客户端发送。
- 源码学习类条目应充分展开技术细节（如模块架构、关键类职责、设计意图），可嵌套多级要点。
- **生成新周报前必须先搜索并阅读已有周报**（步骤 0），确保风格一致、进度可追踪、术语统一。如 `weekly-report/` 目录下无已有周报（首次生成），则跳过参考步骤。
