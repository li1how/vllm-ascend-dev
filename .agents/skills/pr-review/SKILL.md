# PR 源码与架构检视

输入 PR 链接，或仓库与 PR 编号。先读取工作区 README、AGENTS 和目标仓库规则。

## 拉取与整理提交

1. 核对目标仓库、当前分支、HEAD 和 dirty，保留开发现场。拉取 PR，固定 base、
   原始 head 及 merge-base，核对拉取的 SHA，并为原始 head 保留本地 ref。
2. 每个 PR 版本创建独立 worktree：
   - 路径：`tmp/pr-review/<仓库>/pr-<PR编号>-<head短SHA>/`。
   - 分支：`pr-<PR编号>-<head短SHA>`。
   PR 更新 head 时另建版本，保留旧目录和分支，不用于其他 PR。已有路径或分支
   冲突时核对内容，保留用户修改并另取名称，不强制覆盖或自动清理。
3. 以 merge-base 到原始 head 的净改动整理本地提交：一个目的一个提交；多个
   独立目的按依赖顺序拆分。同一目的的实现、测试和文档放在一起，混合文件按
   hunk 或中间版本拆分。只在本次 worktree 的检视分支重写历史，不混入修复，遵循仓库提交约定。
4. 整理后必须满足 `HEAD^{tree}` 与原始 `head^{tree}` 相同，且 worktree 干净。
   可从原始 head 软重置到 merge-base 后分组提交；不一致时修正整理结果，空净
   改动不制造空提交。
5. 每个提交用 `git show --format=fuller --binary --full-index <SHA>` 导出可点击
   的 `.diff`。diff、日志和按需证据放在 worktree 外，按 PR/head 区分。仅整理
   本地历史，不推送、修改远端 PR 或发布评论。

## 深入源码检视

- 从改动入口追踪调用链、数据流、状态所有权和资源生命周期，核对保护逻辑与
  反例。按改动检查正确性、边界、通信同步、异常清理、内存、性能和兼容性；
  并行、缓存和 graph 改动需检查空 rank/batch、集体通信对称性及 buffer 生命周期。
- 核对 PR 配套 vLLM 版本及实现，必要时区分发布版与 main；相邻 checkout 不自动
  代表配套版本。算子相关问题追到包装、注册或分发及实际 C++、AscendC、Triton
  等实现，核对 shape、dtype、layout、写入和同步契约，分清生命周期包装与实际计算。
- 架构和方案同样纳入检视，包括职责分层、重复实现、跨层状态、耦合、扩展成本
  及已有上游扩展点。即使功能正确，也可基于具体代码和代价提出问题；个人风格
  或无证据的未来风险不构成确定问题。对照原版，区分本次引入、加重与既有问题。
- 每个确定问题给出推荐处理方式；架构问题说明更好的职责划分、数据流或集成
  位置，并链接可复用实现。说明改动范围、收益、兼容性与成本；必要时比较最小
  调整和长期方案并明确推荐。替代方案必须覆盖原需求、版本和边界条件，新增
  代码标为建议并链接现有集成位置。预期性能收益不能写成实测收益。

## 小范围验证

- 默认仅在现成环境运行针对性 UT 或算子检查：单项最多 5 分钟，本轮本地与
  远端累计最多 10 分钟。设置超时，记录日志和退出码；失败或超时先分析，不反复重跑。
- 不自动安装依赖、构建、下载权重或启动服务。需要更长验证或服务时，先说明
  要验证的问题、环境、命令和预计耗时，再询问用户；继续不依赖该测试的检视。
- 远端使用用户指定环境，按需使用 [remote-execution](../remote-execution/SKILL.md)
  和 [vllm-runtime-diagnosis](../vllm-runtime-diagnosis/SKILL.md)。核对各仓库 SHA/dirty、
  实际导入路径及原生构建产物版本，不把旧代码的结果算作 PR 验证，也不影响
  正在读取同一源码路径的任务。

## 会话输出

按以下顺序直接在会话交付：

1. **PR 概述**：简述目的和整体前后行为，列出 base/head、merge-base、检视分支、
   worktree 路径及实际核对的配套版本。
2. **提交与模块改动**：给出提交 SHA 和 diff 链接，按模块或执行链路解释“原来
   怎么做、关键修改是什么、现在行为如何变化、为什么”，链接关键文件和函数。
   不要求逐文件列作用；测试仍纳入检视，默认省略介绍，只有用户要求、测试本身
   有问题或构成关键证据时展开。文档和机械改动按需归纳。
3. **检视问题**：编号 R1、R2……，实现与架构问题统一按 P0–P3 排序。每条包含
   类型、具体影响及范围、触发条件或设计代价、原因与源码证据、推荐方案及其
   代码位置和取舍；实现缺陷说明预期与实际行为。标注“源码推导”“已运行复现/
   验证”或“待确认”，缺少关键源码、版本或触发证据时不写成确定缺陷。
4. **验证与缺口**：列出已运行结果和待确认项；未发现确定问题时如实说明。
   更新复核沿用旧问题编号，逐条标明已修复、仍存在或待确认。

| 等级 | 判断参考 |
| --- | --- |
| P0 紧急 | 广泛或必然的服务不可用、严重数据或结果错误 |
| P1 高 | 主要支持路径故障，或严重的性能、资源、架构代价 |
| P2 中 | 特定配置下的问题，或明确的维护、兼容和扩展成本 |
| P3 低 | 局部低影响问题，不以纯风格意见充数 |

等级取决于实际影响，架构问题也可以是高优先级；另说明受影响的模型、硬件、
并行配置和路径，以及正确性、性能、内存、兼容性或维护成本，不能只报等级。

文件、函数和代码证据均使用核对过的本地行号链接：`[名称](/绝对路径/文件.py:123)`，
路径含空格时用尖括号包住链接目标。直接链接本 PR 的独立 worktree，不另存已有
源码快照。旧版本、删除文件或依赖源码优先链接版本匹配的本地文件，必要时仅
导出所引用的准确版本文件并注明仓库/SHA；二进制链接文件和 diff，不伪造行号。
交付前复核 worktree HEAD、tree 一致性及所有链接对应的版本和行号。
